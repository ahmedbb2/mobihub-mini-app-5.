# MobiHub Mini App V1.10.8 — إدارة الورديات وجدول الموظف (TEST)

## أساس الإصدار
- مبني على حزمة V1.10.7 TEST.
- يحتفظ بمسارات الحضور وGPS والطلبات والإجازات والسلف والعهد والتسويات والشكاوى والخصومات والمكافآت والأجهزة والفحص والإشعارات والأوفر تايم ومراجعة الغياب.
- لا يستبدل النشر الحالي ولا يغيّر Cloudflare Worker أو Telegram Webhook.

## الإضافات في V1.10.8

### 1. إدارة الورديات
- عرض دليل الورديات وحالة كل وردية وعدد التعيينات السارية/المستقبلية.
- إنشاء وردية ثابتة بمعرّف فريد، اسم، حضور، انصراف، وفترة سماح.
- إنشاء وردية مرنة واحدة باستخدام المعرّف `FLEX_NO_FIXED_TIME`، دون مواعيد حضور أو انصراف.
- تعديل الاسم والمواعيد وفترة السماح للوردية الثابتة.
- تعديل الاسم وفترة السماح للوردية المرنة، مع الإبقاء على سلوك V46.
- تفعيل/إيقاف الوردية.
- منع إيقاف وردية إذا كان لها أي تعيين نشط لا يزال تاريخ نهايته مفتوحًا أو لم ينتهِ.
- صلاحية الإنشاء والتعديل والتفعيل/الإيقاف: `Super Admin` و`Admin` فقط، مع تحقق السيرفر.

### 2. تعيين الورديات
- الإبقاء على تعيين الموظف للوردية من شاشة شؤون المهندسين.
- تحويل اختيار أيام العمل إلى checkboxes بدل كتابة الأرقام يدويًا.
- الفترة من تاريخ بداية إلى تاريخ نهاية اختياري.
- لا يسمح السيرفر بإسناد وردية ثابتة يوم الجمعة؛ الوردية المرنة يمكن إسنادها لأي يوم.
- عند تعيين فترة جديدة متداخلة لنفس الموظف، تُعطّل التعيينات النشطة المتداخلة قبل إضافة التعيين الجديد، وفق الوظيفة السابقة.

### 3. جدول الموظف
- إضافة بطاقة `جدول الورديات` في مساحة الموظف.
- تعرض جميع التعيينات النشطة، أيام العمل، تاريخ البداية والنهاية، المواعيد وفترة السماح.
- توضح إن كان التعيين ينطبق على يوم العرض الحالي.
- القراءة مقصورة على Chat ID المستخرج من Telegram `initData`؛ لا يقبل API هوية موظف من المتصفح.

## API actions الجديدة
- `shift_create`
- `shift_update`
- `shift_status`
- `my_shifts`

تظل قراءة بيانات الإدارة عبر `list` للكيانين `shifts` و`assignments` خاضعة لفحص الصلاحية الموجود بالفعل.

## اختبارات البناء التي أُجريت
- فحص Syntax لملف Apps Script بعد تحويل امتداده مؤقتًا إلى `.js`.
- فحص Syntax لملف `app.js`.
- فحص HTML IDs وعدم وجود IDs مكررة.
- اختبارات وحدات محلية لإنشاء وتعديل وتفعيل/إيقاف الورديات، منع التكرار، منع إيقاف وردية بتعيين ساري، واسترجاع جدول موظف من تعييناته الخاصة.

## اختبارات لازمة في TEST قبل الاعتماد
1. أنشئ وردية ثابتة مثل 09:00–17:00 وسماح 15 دقيقة.
2. حاول إنشاء نفس Shift ID مرة ثانية؛ يجب أن يرفض.
3. أنشئ الوردية المرنة؛ تأكد من رفض إنشاء وردية مرنة ثانية.
4. عدّل اسم الوردية والمواعيد وفترة السماح.
5. عيّن وردية لموظف واختر الأيام والتواريخ، ثم افتح مساحة الموظف بهذا الحساب واضغط `جدول الورديات`.
6. تحقق من ظهور أسماء الأيام والمواعيد والتاريخ.
7. حاول إسناد وردية ثابتة يوم الجمعة؛ يجب أن يرفض السيرفر.
8. حاول إيقاف وردية مرتبطة بتعيين ساري؛ يجب أن يرفض.
9. أنهِ التعيين أو غيّر الوردية، ثم اختبر إيقاف الوردية.
10. اختبر حساب موظف آخر للتأكد أنه لا يستطيع عرض جدول غيره، واختبر مستخدمًا ليس Admin/Super Admin للتأكد من رفض إدارة الورديات.

## قيود الاختبار
- الحزمة مصدر جاهز للاختبار، لكنها لم تُنشر على Apps Script أو Cloudflare أو GitHub.
- لم يتم إجراء اتصال حي بملف Google Sheets أو Telegram من بيئة البناء.
- لم يتم تغيير أي بيانات مستخدم أو إعداد إنتاجي.
- قبل اختبار الكتابة، استخدم نسخة منفصلة من Google Spreadsheet وتأكد من تطابق أسماء الأوراق ورؤوس الأعمدة مع V46.

## النشر الاختباري
1. احتفظ بنسخة احتياطية من ملفات Mini App الحالية وApps Script الحالي.
2. انسخ `Code.gs` إلى مشروع Apps Script TEST الذي يحتوي على `BOT_TOKEN` و`SPREADSHEET_ID` الخاصين ببيئة الاختبار.
3. انشر إصدار Web App جديدًا من مشروع TEST.
4. ارفع ملفات الواجهة (`index.html`, `app.js`, `styles.css`, `_headers`, `assets/`) إلى استضافة الواجهة الاختبارية فقط.
5. لا تعدّل Worker أو Webhook الحاليين أثناء هذه التجربة.
6. نفّذ حالات الاختبار أعلاه بحسابات موظف وAdmin وSuper Admin.

## Rollback
ارجع إلى حزمة V1.10.7 TEST السابقة باستعادة ملفاتها ونشر إصدار Apps Script السابق. لا توجد تغييرات إنتاجية نحتاج إلى عكسها.
